当前源码基线：本地 checkout f01a0c7f97ec，核对日期 2026-08-13。

验证级别：source-verified、runtime-unvalidated。本文没有在 GPU 上做断点、Tensor dump 或 性能测量；CUDA Graph、Stream 和 kernel 的描述来自当前静态源码。

1. 读完本文应先掌握的结论

一轮 dSpark Decode 不是“Draft 生成多个 token，Target 选几个，然后把选中的 token 全写入 KV”这么简单。当前实现的核心是一个滚动 anchor：

本轮 Target verify 输入： [old_anchor, d1, d2, ..., d_gamma]
本轮用户输出：            [accepted drafts, new_bonus]
本轮 Draft KV 提交：       [old_anchor, accepted drafts]
下一轮 anchor：            new_bonus

若连续接受 k 个 draft，则：

correct_len  = k
commit_lens  = k + 1
new_seq_lens = prefix_lens + k + 1

但 commit_lens=k+1 在两个消费者处代表的 token 内容不同：

用户有效输出长度 k+1： [d1, ..., dk, bonus]
Draft KV 提交长度 k+1： [anchor, d1, ..., dk]

两者长度相同、内容错开一位。bonus 本轮只是 Target 预测结果，没有作为 Transformer 输入， 因此本轮没有自己的 hidden/KV；它到下一轮才作为新 anchor 被处理。

2. 先固定符号、量纲和坐标

符号/字段 严格含义 本文例子
B batch size 1
gamma / G 每请求 proposal 的 draft token 数 4
W Target verify 每请求完整宽度 gamma + 1 = 5
H_d dense Draft Transformer hidden size H_d
H_aux Target FULL 捕获的辅助特征宽度，可能拼接多个 target layer H_aux
V target 原始 vocab size V
prefix_lens 本轮开始前已经具有有效 KV 的逻辑前缀长度 [22]
anchor 上一轮输出、但尚未作为输入写入 KV 的 bonus Y
draft_tokens 本轮 Draft 提议的 gamma 个 token [a,b,c,d]
correct_len 连续接受的 draft 数，不包含 anchor/bonus 1
commit_lens correct_len + 1 2
bonus 接受前缀后由 Target 分布得到的下一个 token Z
new_seq_lens 下一轮开始前的有效 KV 逻辑长度 [24]

必须始终保持以下量纲关系：

gamma = 4
W = verify_num_draft_tokens = gamma + 1 = 5

Draft Transformer block： [anchor, MASK, MASK, MASK]      宽度 4
Target verify candidates： [anchor, d1, d2, d3, d4]      宽度 5

如果启用 confidence scheduling，还要注意坐标偏移：

confidence position p  ↔  draft d_(p+1)  ↔  verify column p+1
verify column 0        ↔  anchor

因此 min_verify_len=1 只保底 anchor，不代表保底验证一个 draft。

5. 本轮入口状态和 VerifyWindow

5.1 prefix_lens=[22] 不包含 anchor Y

本轮开始前：

有效 KV positions： 0 ... 21
prefix_lens：        22
待处理 anchor：      Y @ position 22

Y 在上一轮已经作为 bonus 输出给用户，但上一轮没有把 Y 当作 Transformer 输入，因此 它还没有自己的 hidden/KV。本轮必须先以 Y 为 anchor。

6. DraftBlockProposer：一次并行 Transformer + 串行 Markov 采样

6.1 Draft Transformer 的输入不是 [Y,a,b,c,d]

DraftBlockProposer._run_forward() 位于 python/sglang/srt/speculative/dspark_components/dspark_draft.py:361-426。

它构造：

draft_block_ids = [Y,MASK,MASK,MASK]        shape [1,4]
draft_positions = [22,23,24,25]             shape [4]
draft_cache_loc = [L22,L23,L24,L25]         shape [4]

Draft 只取完整 VerifyWindow 每行的前 gamma=4 个槽。Target verify 才使用宽度 W=5 的 [Y,a,b,c,d]。

6.2 实际构造的 draft_forward_batch

本文例子中的字段是：

batch_size 1 一个请求

这里最容易误读的是：

seq_lens      = [22]
seq_lens_cpu  = [26]

在这个手工构造的 speculative ForwardBatch 中，两者不是逐值镜像：GPU rail 保存进入 block 前的 prefix；CPU rail已经加上本次规划的 G 行。batch.seq_lens_cpu + gamma 创建新 Tensor，不会把 Scheduler 持久的 CPU length 原地改成 26。

6.3 为什么四个输入位置能产生四个 draft

Draft Transformer 一次并行 forward：

[Y,M1,M2,M3]
   │
   ▼
draft_hidden = [h0,h1,h2,h3]                shape [1,4,H_d]
   │
   ▼ shared Target LM Head
base_logits = [l0,l1,l2,l3]                 shape [1,4,V]

然后 Markov head 串行注入真实的前一 token：

上图使用统一通式；具体 Markov head 有边界差异：vanilla 主要加入 previous-token bias，gated 还读取当前 draft_hidden_i，RNN 还携带跨位置 recurrent state。它们共同保持“Transformer 一次、Markov logits 修正/采样串行”的主结论。

因此：

  • Draft Transformer 只跑一次；
  • 后置 Transformer hidden 看到的是 causal prefix 加 MASK 占位符，不是刚采样出的 a/b/c；
  • 串行的是 Markov logits 修正与采样，不是四次 Transformer forward；
  • Markov 不会回头改写已经算完的后置 hidden/KV。

6.4 DraftProposal 包含什么

定义位于 dspark_draft.py:51-71：

DraftProposal
├── draft_block_ids      [Y,M,M,M]
├── draft_block
│   ├── draft_tokens     [a,b,c,d]
│   ├── corrected_logits [1,4,V]，folded greedy 时可为 None
│   ├── greedy_mask      [1]
│   └── temperatures     [1]
├── draft_hidden         [1,4,H_d]
├── confidence           可选
├── confidence_tap       可选
└── folded               sampler tail 是否折入 Draft CUDA Graph

corrected_logits 是实际 proposal 分布 q 的未除温 logits。Sampling verify 后续用它重建 q；greedy 不需要概率修正，folded greedy 因而可以不返回这块大 Tensor。

6.5 greedy 与 sampling 的 Draft 边界

resolve_greedy_mask() 以 top_k <= 1 判断每个请求是否 greedy，见 dspark_draft.py:166-238：

greedy：   每步 argmax，不随机抽样
sampling：softmax(corrected_logits / temperature) 后随机抽样
mixed：    同一 batch 内按请求 greedy_mask 选择

Draft proposal 侧 sampling 不应用 Target 的 top-k/top-p 截断；这是允许的，因为 Target 接受阶段 会使用实际 q 做拒绝采样修正。Target 的 temperature/top-k/top-p 决定目标分布 p。

7. 从 DraftProposal 到 Target candidates

7.1 先建立 Planner 的组件边界

Worker 在 worker_v2.py:538-570 依次处理：

confidence
→ resolve_verify_token_budget()
→ schedule_layout()
→ should_run_compact()

这条链涉及 Draft graph、Worker、Host planner、Scheduler/FutureMap 和下一步 layout 分配，不能把 它们压成一个“按 confidence 裁剪”的动作：

这几个量必须始终分开：

当前 confidence C_t：       本轮各 draft 位置的条件置信分数
历史 survival S_(t-2)：     历史 confidence 沿 draft 前缀的累计乘积
budget_t：                  整个 batch 在 mandatory floor 外可分配多少个额外槽
verify_lens_t[B]：          当前 confidence 将 budget 分配给各请求后的长度，包含 anchor

因此默认稳态职责是：

历史 C_(t-2) 决定“选多少”
当前 C_t     决定“分给谁”

confidence/budget/layout 都不改变 Draft proposal 分布 q，也不替代后续 greedy matching 或 rejection sampling；在后续确实产生 non-None layout 时，它们决定 Target 本轮值得验证到多深， 以及 COMPACT 是否有机会减少有效候选行。STATIC、预算/relay 尚未就绪或 captured-grid fallback 都可能不产生 layout。

7.2 compute_confidence_tensor()：得到当前 C_t[B,G]

Worker 先复用 proposal 中可能已经存在的结果，见 dspark_worker_v2.py:538-545：

confidence = proposal.confidence
if confidence is None:
    confidence = self._verify_planner.compute_confidence_tensor(
        draft_hidden=proposal.draft_hidden,
        anchor_tokens=draft_block_ids[:, 0],
        draft_tokens=draft_tokens,
        confidence_tap=proposal.confidence_tap,
    )

proposal.confidence 非空表示 folded greedy Draft CUDA Graph 已在 sampler tail 中算完 confidence； Worker 直接复用，避免重复计算。普通 eager/sampling 路径通常为 None，再进入 DSparkVerifyPlanner.compute_confidence_tensor()，见 dspark_planner.py:264-293：

confidence_head 不存在： 返回 None（正常 STATIC 路径）
模型有 compute_confidence hook：使用 confidence_tap（DeepSeek-V4）
否则：使用 dense 通用 compute_confidence()

下面固定一个 multi-request 教学例：

B = 2
G = 4

anchor_tokens = [Y0,Y1]                              shape [2]
draft_tokens  = [[a,b,c,d], [e,f,g,h]]               shape [2,4]
draft_hidden                                              [2,4,H_d]

dense 通用 helper 位于 dspark_planner.py:888-923。它先构造每个 draft 位置的真实前驱 token：

prev_seq = torch.cat(
    [anchor_tokens.view(-1, 1), draft_tokens[:, : gamma - 1]],
    dim=1,
)
markov_embed_stack = markov_head.get_prev_embeddings(prev_seq)

代入数据：

prev_seq = [[Y0,a,b,c],
            [Y1,e,f,g]]                              shape [2,4]

markov_embed_stack                                  shape [2,4,R]

坐标含义是：

confidence[:,0] 评估 d1，前驱是 anchor
confidence[:,1] 评估 d2，前驱是 d1
confidence[:,2] 评估 d3，前驱是 d2
confidence[:,3] 评估 d4，前驱是 d3

默认 with_markov=True 时，DSparkConfidenceHead.forward() 在 models/dspark.py:289-330 执行：

draft_hidden                                  [2,4,H_d]
markov_embed_stack                            [2,4,R]
cat(..., dim=-1)                              [2,4,H_d+R]
Linear(H_d+R → 1)                             [2,4,1]
squeeze(-1) = confidence_raw                  [2,4]

随后 STS calibration：

confidence = torch.sigmoid(
    confidence_raw.float() / sts_temperatures
)

sts_temperatures 是 confidence 的标量或逐位置 [G] 校准温度，不是生成 sampling temperature。最终 confidence[B,G] 每项在 [0,1]，但四列不需要和为 1；它不是 vocab 分布、不是 proposal P_D，也还不是累计 survival。

本节后续使用一组教学输出：

C_t = current confidence =
req0 [0.95, 0.90, 0.70, 0.20]
req1 [0.99, 0.95, 0.92, 0.85]                 shape [2,4]

三条模式边界：

  • STATIC 在模型构造阶段就不创建 confidence head，全链返回 None；正确性不受影响，只是不做 自适应验证深度调度。
  • folded greedy graph 在 dspark_draft.py:79-118,290-315 内计算并写入 confidence_out[max_bs,G]，Worker 只取 live batch slice；proposal.folded=True 不代表 Target accept/commit 也 folded。
  • DeepSeek-V4 在 deepseek_v4_dspark.py:714-758 使用 collapse 后的 confidence_tap，不能把 dense [B,G,H_d] 形状直接套过去；最终输出仍为 [B,G]。

7.3 resolve_verify_token_budget()：只决定 batch-global 数量

Worker 立即调用 dspark_worker_v2.py:547-552：

verify_token_budget = self._verify_planner.resolve_verify_token_budget(
    draft_input=draft_input,
    confidence=confidence,
    prefix_lens=prefix_lens,
    req_pool_indices=batch.req_pool_indices,
)

方法定义见 dspark_planner.py:373-391：

if not self.schedules_verify_budget or confidence is None:
    return None
if not self.server_args.disable_overlap_schedule:
    return draft_input.verify_token_budget
return self.compute_budget_sync(
    confidence=confidence,
    prefix_lens=prefix_lens,
    req_pool_indices=req_pool_indices,
)

它返回 Optional[int]，不是每请求 Tensor。继续固定：

B = 2
G = 4
W = G + 1 = 5
min_verify_len = 1

量纲如下：

数量 本例 是否属于 budget
mandatory anchor floor B×1=2 否，另算
可选 draft positions B×G=8 是，构成候选池
完整 Target verify 上限 B×W=10 floor 与全部 extra 之和

因此 budget=5 的严格含义是：

两个 anchor 之外，整个 batch 最多再分配 5 个 draft verify 槽
逻辑 allowance 上限 = floor 2 + budget 5 = 7 行

它不表示“每请求 5 行”，也不能直接推出 verify_lens=[3,4]；下一步还必须使用当前 C_t 分配这 5 个名额。

7.4 non-overlap：当前 C_t 入参，历史 C_(t-2) 参与 optimizer

non-overlap 时 resolve_verify_token_budget() 进入 compute_budget_sync()，见 dspark_planner.py:351-371：

当前 C_t [B,G] GPU
→ C_t.to("cpu")
→ 读取 req_pool_indices 对应的 generation
→ ResolvedConfidence(C_t, generation)
→ HostConfidenceBudgetPlanner.compute_budget()

因此只看外层会误以为当前 C_t 立即参与 budget；真正的轮次选择在 HostConfidenceBudgetPlanner._shift_to_lag()。初始化代码是：

relay_lag_steps = 0 if disable_overlap_schedule else CONFIDENCE_RELAY_RING_LAG

self.lag_steps = max(
    SGLANG_DSPARK_CONFIDENCE_RELAY_LAG_STEPS,
    1,
)
self.carry_steps = max(self.lag_steps - relay_lag_steps, 0)

当前默认：

lag_steps       = 2
relay_lag_steps = 0       # non-overlap 没有 FutureMap confidence relay
carry_steps     = 2

_shift_to_lag() 在 dspark_planner.py:1087-1104 的关键顺序是“先读旧值，再写当前值”：

lagged_confidence = self._carry_confidence[slot, rows].clone()
lagged_generation = self._carry_generation[slot, rows].clone()
self._carry_confidence[slot, rows] = confidence
self._carry_generation[slot, rows] = generation
return lagged_confidence, lagged_generation

同一请求连续出现时：

当前调用 当前传入 optimizer 实际读取 写回 carry
t=0 C0 初始空槽 → freshness fallback C0
t=1 C1 初始空槽 → freshness fallback C1
t=2 C2 C0 C2
t=3 C3 C1 C3
t=4 C4 C2 C4

所以默认稳态：

budget_t = optimizer(cumprod(C_(t-2)), SPS cost)

当前 C_t 一方面写入 carry 供未来 budget 使用，另一方面在本轮后续直接交给 schedule_layout()，用于决定“名额分给谁”。

req_pool_indices 还会配合 req_generation 防止 request-pool row 复用：旧历史 generation 与 当前请求不匹配时，_two_steps_prior_survival() 使用全 1 survival，而不是把旧请求的低 confidence 应用给新请求。prefix_lens 当前在 compute_budget_sync() 中被明确 del，所以这个 optimizer 并不直接按上下文长度决定 budget。

7.5 overlap：两轮延迟由 FutureMap/ConfidenceRelay 实现

overlap 下 Worker 不现场调用 compute_budget_sync()，只读取 draft_input.verify_token_budget。这个字段定义于 dflash_info_v2.py:35-57，由 Scheduler 在 Worker forward 之前调用 prepare_verify_budget() 写入：

Scheduler 调用点在 scheduler.py:3398-3425；本轮 Worker 在接受后通过 dspark_worker_v2.py:641-645 发布 C_t，FutureMap.publish() 再写 confidence relay。

默认 overlap 参数：

lag_steps       = 2
relay_lag_steps = CONFIDENCE_RELAY_RING_LAG = 2
carry_steps     = max(2 - 2, 0) = 0

因此默认稳态下，两种执行模式使用同样历史年龄：

模式 两轮延迟在哪里实现 Host 额外 carry budget 使用
overlap FutureMap/ConfidenceRelay D2H ring 0 C_(t-2)
non-overlap HostConfidenceBudgetPlanner carry ring 2 C_(t-2)

两者的区别不是“一个用当前、一个用历史”，而是两轮延迟由哪个组件承担。warm-up 行为则不同：

  • overlap ring 尚未积累两轮或 copy event 未完成时，resolved confidence 可能为 None，budget 也为 None；
  • non-overlap 初始 carry generation 不匹配，survival 回退为全 1，再结合 SPS table 计算 budget。

上述 C_(t-2) 是同一请求连续 decode、generation 匹配时的稳态说法；batch 交错、非 decode step、request-pool row 复用或 relay 未就绪时，要按上述 fallback 理解，不能机械地把每个请求 都标成严格的物理“前两轮”。

7.6 compute_verify_token_budget()：历史收益与 SPS 成本的折中

Host planner 先计算：

history_survival = torch.cumprod(lagged_confidence, dim=1)

使用另一组明确标为历史的教学数据，避免和当前 C_t 混淆：

C_(t-2) =
req0 [0.90, 0.80, 0.50, 0.20]
req1 [0.70, 0.60, 0.50, 0.40]

S_(t-2) = cumprod(C_(t-2)) =
req0 [0.900, 0.720, 0.360, 0.072]
req1 [0.700, 0.420, 0.210, 0.084]

compute_verify_token_budget() 位于 dspark_planner.py:954-991，依次执行：

flatten 全 batch survival
→ 删除低于 survival_eps 的候选
→ survival 降序排序
→ prefix_sum
→ 对每个 k=0..N 估算收益与成本
→ 取 objective 最大的 k 作为 budget

排序结果：

[0.900, 0.720, 0.700, 0.420, 0.360, 0.210, 0.084, 0.072]

对于 budget 候选 k，预期每 step 进度是：

tau_star(k) = B + sum(top-k historical survival)

其中基础项 B=2 表示每个请求即使一个 draft 都不接受，也至少由 anchor 的 Target logits 产生一个 bonus 输出。假设教学用 SpsCostTable 是：

SpsCostTable(
    sample_batch_tokens=[1, 5],
    sample_steps_per_sec=[1.0, 0.5],
    max_batch_tokens=10,
)

该表按 floor probe 查询：B+k<5 时 SPS 为 1.0，从 5 tokens 起为 0.5。于是：

k B+k tau_star(k) SPS theta=tau_star×SPS
0 2 2.000 1.0 2.000
1 3 2.900 1.0 2.900
2 4 3.620 1.0 3.620
3 5 4.320 0.5 2.160
4 6 4.740 0.5 2.370
5 7 5.100 0.5 2.550
6 8 5.310 0.5 2.655
7 9 5.394 0.5 2.697
8 10 5.466 0.5 2.733

最大值位于 k=2，所以：

VerifyBudgetDecision.budget = 2
resolve_verify_token_budget() = 2

这仍只表示“两个 anchor 之外，整个 batch 额外开放两个 draft 槽”。下一节才会使用当前 C_t 决定这两个槽给 req0、req1 的哪些位置。

普通 SpsCostTable 的目标是 tau_star × steps_per_sec；SpsAdditiveCostTable 则使用 tau_star / step_time(B,k)，但最终都返回 batch-global scalar budget=argmax_k objective(k)。 完整 VerifyBudgetDecision 还保存预测 step time 和 objective，resolve_verify_token_budget() 只返回其中的 Python int。

没有 profile SPS 文件时，源码构造 constant-SPS flat table。因为 survival 非负，prefix sum 和 tau_star 单调不减，optimizer 通常选择全部高于 survival_eps 的候选，退化为 verify-all； 不是 budget=None。min_verify_len 的 floor 也不在这个 optimizer 中扣除，而由后续 verify-lens scheduler 保证。

7.11 STATIC、CAP_ACCEPT、COMPACT 必须分开

模式 layout/verify_lens Target forward 接受阶段
STATIC 始终 layout=None 完整 B×W 按真实匹配/拒绝采样
CAP_ACCEPT 有 confidence/budget 时可有；否则可为 None 始终完整 B×W 有 layout 时将 correct_len 截到 verify_len-1
COMPACT 通常有；超出 captured grid 等情况可返回 None 有 layout 时构造 compact buffer；无 layout 时 fallback 到 full-width non-compact 再按相同 accept/cutoff 规则处理

只有 COMPACT 有能力在 Target Transformer 前裁掉未选择的候选；CAP_ACCEPT 即使有 verify_lens，也不节省本轮 Target forward 计算。但 COMPACT 的物理输入长度是 layout.graph_num_tokens，可能大于 sum(verify_lens)，其中包含 CUDA Graph tier padding；若 verify-all、padding 填满完整 tier，或 layout fallback 为 None，本轮也可能没有实际计算节省。

决定分支的精确条件是：

run_compact = (mode == COMPACT) and (layout is not None)

COMPACT 配置下若 schedule_layout() 返回 None，Worker 改走完整宽度 non-compact；当前 compact-configured graph runner 对 TARGET_VERIFY + 无 ragged layout 也不会强行 replay ragged graph，而是落到 full-width eager fallback。

8.3 真正的 Target forward 与 runner 边界

两条入口最终都调用：

    batch=None,
    forward_batch=verify_forward_batch,
    is_verify=True,
    skip_attn_backend_init=True,
)

调用点在 dspark_verify.py:262-285。

TARGET_VERIFY 不等于必然 Eager。prepare_for_verify() 先做 execution pre-plan：decode CUDA Graph 可运行时调用 graph runner 的第一次 load_batch()；否则调用 Target attention backend 的 init_forward_metadata() 规划 eager metadata。第一次 graph load_batch() 在本例记录：

raw_bs          = 2
raw_num_token   = graph_num_tokens = 5
graph key       = 5              # ragged graph 按 token tier key
capture slots   = 5              # 通常 min(graph_num_tokens,max_bs)

随后 target_worker.forward_batch_generation(..., is_verify=True, skip_attn_backend_init=True) 把 ForwardBatch 标为 metadata-ready。进入 ModelRunner._forward_raw() 后，若 graph 仍可用，execute() 内会第二次调用 load_batch()；这次 只刷新静态 input_ids[:5]、positions[:5] 与 graph key，复用第一次计划的 metadata，再 replay。

所以两次 load_batch() 不是重复工作：

第一次：完整 pre-plan + static rail copy + attention metadata + graph key
第二次：replay 前轻量刷新 ids/positions + 复用既有 plan

graph 不可用时，ModelRunner 准备 eager batch，最终进入 EagerRunner._execute_extend()；虽然 通用 extend 分支还会检查 prefill graph，但 PrefillCudaGraphRunner.can_run_graph() 对 TARGET_VERIFY 明确返回 False，所以当前不会进入 piecewise Prefill CUDA Graph。更重要的是：

COMPACT + decode graph 失败 = eager compact，仍 forward 5 个物理 rows

它不会在这里重新变成完整矩形 10 行；只有更早的 layout=None → run_compact=False 才走 full-width non-compact。

这里的 skip_attn_backend_init=True 也不表示 metadata 从未初始化；它表示 pre-plan 已完成， 正式 forward 不应再次规划并覆盖它。

不同 backend 对请求分段的消费字段不同：FlashAttention/TRT-LLM MHA 主要把 qo_indptr_device 用作 cu_seqlens_q；DeepSeek-V4 会直接消费 extend_start_loc 展开其 prefill/causal metadata。普通 FlashInfer 当前没有 opt-in ragged graph，device-only layout 的 eager helper 也需要非空 host total；这是静态源码暴露出的兼容性边界，本文未做对应 GPU 配置验证。

compact rows 2,3 → strided req1 columns 0,1
compact padding row 4 → sink，不进入真实请求

strided req0 = [row(Y0), row(a), 0, 0, 0]
strided req1 = [row(Y1), row(e),  0, 0, 0]

这里的 0 表示 logits/hidden 的 fill value，不是一个被 Target 计算并接受的 token id。5→10 只是恢复公共 accept 接口所需的请求主序布局，不是 Target 又 forward 了 10 行。若 graph epilogue 已捕获这段 scatter，则 run_compact() 直接读取预写的 strided buffers，数据语义相同、执行位置 不同。

TargetVerifyResult 外壳是 frozen，但其 logits_output 内部对象可变；run_compact() 会将 logits_output.next_token_logits/hidden_states 替换成 strided Tensor。因此“TargetVerifyResult 是 compact 还是 strided”必须附带上述观察时刻。

若有 grammar，Worker 会在 worker_v2.py:614-625 对 Target logits 应用 grammar mask，然后 才进入接受阶段。Sampling 的温度、top-k、top-p 需要再拆成两层：verify 路径会先对 strided logits 应用可直接表达为 logits adjustment 的部分；真正进入 AcceptSampling 后，再由 build_dflash_verify_target_probs() 按 temperature → top-k → top-p 构造每个验证位置的目标分布 P_T，供拒绝采样使用。不能把这两层都概括成“普通 sampler 已经采完”；is_verify=True 正是 跳过普通生成 sampler，最终 token 由后续 speculative accept 产生。

8.5 2 / 4 / 5 / 10 四种数量不可混用

数量 本例值 由谁表达 是否代表真实请求
请求数 2 ForwardBatch.batch_size 是
逻辑 compact rows 4 sum(verify_lens) / qo_indptr[-1] 是，属于两条真实请求
物理 Target rows 5 graph_num_tokens / input_ids.numel() 前 4 行是，最后 1 行是 padding
公共 strided rows 10 B×W 是固定接口容量，不等于实算行数

这四个量也是 compact verify 最重要的审计不变量：2 个请求可以对应 5 行 Target 输入； TargetVerifyResult 可以暂时有 5 行；公共 accept 最终看到 10 行固定布局，但 Target 从未因此 计算 10 行。

9. Accept：从 Target logits 得到 correct_len 与 bonus

9.1 对齐关系

假设 Target 各输入行的 next-token 预测是：

Target 输入：       Y   a   b   c   d
Target next 预测：  a   Z   ?   ?   ?

真正比较的是：

draft candidates：      a   b   c   d
Target 对齐预测：       a   Z   ?   ?
                        ✓   ✗

因此：

correct_len = 1
bonus       = Z

Z 来自输入 a 那一行的 Target 分布；它不是输入 b 后得到的结果。

9.2 greedy

accept_and_finalize() 位于 dspark_verify.py:91-149，它先调用 accept_draft_tokens()；全 greedy 分支进入 AcceptGreedy，见 dspark_verify.py:658-678。

greedy 的含义是：

连续从 d1 开始与 Target argmax 比较
遇到第一个不匹配立即停止
bonus = 停止位置对应的 Target argmax

本例接受 a，拒绝 b。即使后面某个 c/d 恰好等于某行 Target argmax，也不能继续提交， 因为那些 Target 行的 causal context 已经包含未接受的 b，不再对应真实生成历史。

greedy 不需要概率修正：Target 分布和 Draft proposal 都退化成单点选择；相等就接受，不相等就 使用 Target token。

9.3 sampling

非 greedy 路径在 dspark_verify.py:679-722 使用 corrected_logits/temperature 重建实际 proposal 分布 q，再由 AcceptSampling 使用 Target 分布 p 做链式拒绝采样：

接受 draft d 的概率 = min(1, p(d) / q(d))
第一次拒绝后的 bonus ~ normalize(max(p - q, 0))
若全部 draft 接受，最终 bonus ~ p

如果残差分布中多个 token 概率为正，kernel 会按 CDF 随机采出一个 bonus，不会取 argmax， 也不会把多个候选一起返回。因此 sampling 模式的 bonus 不一定等于 Target argmax。

9.4 AcceptOuts

普通非 folded 路径依次执行：

accept_draft_tokens()
→ correct_len / bonus / cap_trim_lens
→ FinalizeAcceptLens
→ BuildOutTokens
→ AcceptOuts

AcceptOuts 定义在 dspark_verify.py:444-450：

correct_len
bonus
cap_trim_lens
commit_lens
new_seq_lens
out_tokens

本例：

correct_len   = [1]
bonus         = [Z]
cap_trim_lens = [0]

cap_trim_lens 记录任意 cutoff layout 将原始接受长度额外裁掉多少，不只属于 CAP_ACCEPT： CAP_ACCEPT 和 COMPACT 都可能传入 verify_lens；STATIC/no-layout 为 0。裁剪公式是：

capped_correct_len = min(raw_correct_len, verify_len - 1)
cap_trim_lens      = raw_correct_len - capped_correct_len

裁剪后还必须按新的 correct_len 重新选择 bonus，不能沿用原始更深位置的 bonus。例如 raw_correct_len=3、verify_len=2 时，最终 correct_len=1、cap_trim_lens=2，bonus 必须来自 截断边界 index 1 对应的 Target/residual 结果。

11. KV 提交：写入的是 [Y,a]，不是 [a,Z]

11.1 Target hidden 与输入行对齐

Target forward 的 hidden 是：

Target hidden： [hY,ha,hb,hc,hd]

non-compact 的 commit_hidden() 位于 dspark_verify.py:287-318。它将 hidden reshape 为 [B,W,H_aux]，再把完整位置/物理 slot 和 commit_lens 交给 TargetHiddenKvInjector.inject_target_hidden()。

本例：

有效 target hidden prefix = [hY,ha]

11.2 compact 与 non-compact 的注入路径不同

两条路径提交的逻辑 token 都是 [anchor, accepted drafts]，但位置/cache layout 的来源不同：

non-compact:
  logits_output.hidden_states + VerifyWindow
  → inject_target_hidden(..., commit_lens)

compact:
  run_compact() 返回的 hidden_strided
  → inject_ragged(..., commit_lens)
  → 重建 compact commit 所需的 positions/cache layout

compact 不能只靠 TargetVerifyResult 描述完整后处理；hidden_strided 是 Worker 单独保存并交给 commit_hidden(run_compact=True) 的 side channel。若 folded_commit=True，graph epilogue/pool 已经完成融合写入，Python 两条 commit_hidden 分支都跳过。

11.3 为什么要把 Target hidden 注入 Draft KV

Draft 模型拥有自己的 KV cache。下一轮 Draft 不能只知道 token id，还要拥有已确认历史在 Draft 层中的 K/V 表示。当前 dense dSpark 通过：

Target hidden
→ draft_model.project_target_hidden()
→ draft 各层 K/V projection + RoPE
→ Draft token_to_kv_pool

入口在 python/sglang/srt/speculative/dspark_components/dspark_kv_inject.py:31-78；dense 写入实现位于 python/sglang/srt/models/dspark.py:505-550。

11.3.1 “一个 token 一个 hidden”要加上层坐标

对 Target 的某一层而言，一个 token 确实只有一个 hidden vector：

h_t^(layer_i) ∈ R^H_target

Target 正常生成 logits 通常消费最后一层 hidden：

h_t^(final) → norm → target lm_head → logits_t

dSpark 另开一条 auxiliary capture 路径。Target runner 根据 Draft 配置选择一个或多个 Target layer；如果选择 K 层，同一 token 会得到 K 个带层坐标的 feature：

h_t^(l1), h_t^(l2), ..., h_t^(lK)
              ↓ 按 feature 维拼接
target_hidden_t = [h_t^(l1) | h_t^(l2) | ... | h_t^(lK)]

因此对 N 个 Target 输入行，capture 输出概念形状是：

target_hidden [N, H_aux]
H_aux = K × H_target

若配置只选择一层，K=1，这里就退化为每 token 一个 vector。选择规则在 python/sglang/srt/model_executor/model_runner_components/spec_aux_hidden_state.py:97-165； CaptureHiddenMode.FULL 的含义是捕获本轮所有输入 token 的这些 feature，而不是“捕获所有 Target 层”。

两条箭头不能混为一谈：logits 分支决定 Target 分布；aux hidden 分支负责构造 Draft 历史 KV。

11.3.2 多个 Target feature 先融合成一个 Draft context vector

DFlashDraftModel.project_target_hidden() 位于 python/sglang/srt/models/dflash.py:388-400。它不是直接生成 KV，而是先做一次融合：

u_t = RMSNorm(FC(target_hidden_t))

target_hidden_t [H_aux]
        ↓
u_t             [H_d]

对完整 batch：

target_hidden [N,H_aux]
→ project_target_hidden()
→ ctx_hidden  [N,H_d]

所以“捕获了多个 Target 层”不表示 Target layer 与 Draft layer 一一对应。多个 Target feature 先融合为每 token 一个 ctx_hidden，再进入下一阶段。

11.3.3 一个 ctx_hidden_t 如何展开成 Draft 各层 K/V

这里确实是一对多关系。Draft 有 L_d 层，每层拥有不同的 KV projection 权重：

Draft layer 0: (K_t^0, V_t^0)         = KVProj_0(ctx_hidden_t)
Draft layer 1: (K_t^1, V_t^1)         = KVProj_1(ctx_hidden_t)
...
Draft layer L_d-1: (K_t^(L_d-1), V_t^(L_d-1)) = KVProj_(L_d-1)(ctx_hidden_t)

概念 shape 是：

ctx_hidden [N,H_d]
    ↓ 每个 Draft layer 各自投影
K/V [L_d,N,num_kv_heads,head_dim]

这不是把同一份 K/V 复制 L_d 次：每层的 projection 权重不同，所以每层产生不同的 K_t^j/V_t^j。dense 实现见 python/sglang/srt/models/dspark.py:505-550；其中 stacked 优化把各层 projection weight 拼成一次大矩阵乘法，但数学结果仍等价于逐 Draft layer 投影。

随后 K 还会经过该 Draft 层的 K-Norm 和对应 position 的 RoPE，再写入 Draft 自己的 KV pool。Target/Draft 可以使用对齐的物理 slot index，但写入内容不是复制 Target K/V，而是由 Target hidden 经 Draft projection 新计算出的 Draft-side K/V。

11.3.4 是否每个 token 都写到 Draft 对应位置

结论是：每个需要 commit 的 Target 输入 token，都会在每个 Draft layer 的对应 slot 写入一份 layer-specific K/V；Target 虽已计算但未提交的候选不会成为 Draft 有效历史。

对 token t：

logical position = positions[t]      # 用于 RoPE
physical slot    = cache_loc[t]      # Draft KV pool 写地址

Draft layer j, slot cache_loc[t] ← (K_t^j, V_t^j)

两种阶段的范围不同：

阶段 Target hidden 覆盖 写入 Draft KV 的 token
Prefill/Extend 本次新增 prompt token 本次新增且有效的所有 token
Decode Target Verify [anchor,d1,...,dG] 中本轮实际 forward 的候选行 仅 [anchor, accepted drafts]，由 commit_lens 限制

仍用本节示例：

Target 输入：       [Y, a, b, c, d]
Target hidden：     [hY,ha,hb,hc,hd]
correct_len：       1
commit_lens：       2

Draft 每一层写入： position 22 / slot L22 ← Y 对应的 K/V
                  position 23 / slot L23 ← a 对应的 K/V
Draft 每一层不写： b、c、d 对应的未提交候选位置

set_kv_buffer_prefix_valid(..., commit_lens, ...) 在每个请求的 verify row 中只开放前 commit_lens 列。compact 路径虽然先把 hidden scatter 成 strided layout，再由 inject_ragged() 重建写入几何，但遵守同一个 commit mask。

11.3.5 Prefill 与 Decode 的完整调用入口

Prefill:
DSparkWorkerV2._forward_prefill()
→ target forward(capture_hidden_mode=FULL)
→ logits_output.hidden_states
→ TargetHiddenKvInjector.inject_target_hidden()
→ Draft KV pool

Decode Verify:
TargetVerifyExecutor.run_non_compact()/run_compact()
→ target forward(capture_hidden_mode=FULL)
→ accept 得到 commit_lens
→ commit_hidden()
→ inject_target_hidden()/inject_ragged()
→ Draft KV pool

项目内交互图解见 dSpark Target Hidden → Draft KV 逐步讲解器。

set_kv_buffer_prefix_valid(..., commit_lens, ...) 只提交每请求前 commit_lens 行：

Draft KV 新增：
position 22 → Y
position 23 → a

b/c/d 即使在完整 Target verify 中被计算过，也不属于下一轮逻辑有效前缀。Target 侧同样只把 逻辑 new_seq_lens 推进到 24；超出接受前缀的候选物理写入不能被当成 committed history。

11.4 为什么 Z 本轮没有 KV

自回归对齐是：

输入 a
→ 得到 ha
→ lm_head(ha)
→ 采样/argmax 得到 Z

Z 是输出，不是本轮输入，因此当前没有 hZ/KZ/VZ。如果直接把 Z 当成已写入 KV，下一轮 会错误地跳过对 Z 的 Transformer 计算。

12.3 non-overlap Scheduler 交接

12.3.1 resolve_forward_inputs() 没有被跳过

non-overlap speculative 分支在 python/sglang/srt/managers/scheduler.py:3500-3521 中仍然真实调用：

resolve_forward_inputs(batch, self.future_map)
with self._forward_isolation(batch, overlap=False):
    batch_result = self.model_worker.forward_batch_generation(batch)

因此，准确结论不是“non-overlap dSpark 跳过了 resolve_forward_inputs()”，而是：

普通 non-overlap dSpark pure decode 会进入该函数；只是三个可能修改状态的 guard 都没有命中，所以函数作为一次 guard-only no-op 返回。

函数位于 python/sglang/srt/managers/overlap_utils.py:84-115。固定 pure decode 状态逐项代入：

resolve_forward_inputs() 内的修改路径 本例关键条件 是否执行
Prefill CPU staging → GPU batch.prefill_input_ids_cpu is not None 为 False 否，不做 H2D，也不拼 mixed decode token
ordinary non-spec Decode gather batch.input_ids is None 为 True，但 future_map.spec_algo.is_none() 为 False 否，不从 output_tokens_buf gather
overlap speculative extras batch.enable_overlap 为 False 否，不调用 _resolve_spec_extras()

第二个 guard 检查的是 future_map.spec_algo，不是 batch.spec_algorithm。dSpark FutureMap 的算法不是 NONE，所以即使 batch.input_ids is None，整个 elif 条件仍为假。

这个 no-op 结论有严格边界：它只描述本文固定的 pure decode 状态。若 prefill_input_ids_cpu 非空，即使仍处于 non-overlap speculative 路径，第一个分支也会把 CPU staging 输入搬到设备；Mixed batch 还会从 FutureMap 取 running decode token，再和 prefill token 拼接。换句话说，non-overlap 决定不了该函数是否改状态，三个运行时 guard 才决定。

12.3.2 resolver、isolation 与显式提交的先后顺序

resolve_forward_inputs() 在 _forward_isolation() 外部且之前执行；resolver 返回后， context manager 才对 ScheduleBatch 字段做浅快照。Worker 返回时，isolation 恢复进入 context 时的字段绑定，Scheduler 再从 GenerationBatchResult 显式提交真正需要跨轮保存的结果：

_forward_isolation() 的当前实现位于 python/sglang/srt/managers/scheduler.py:3325-3367。对 spec V2，它先保存 dataclass 的字段引用， 再让 Worker 临时改写 forward_mode/input_ids/seq_lens/spec_info/...，最后逐字段恢复。它隔离的是 Worker forward 期间的临时 rebind；不能把它解释成“回滚 resolver”：

  • pure dSpark Decode 中 resolver 本来就是 no-op；
  • speculative Prefill 中，resolver 若先物化了 input_ids，这个结果会成为随后 snapshot 的基线；
  • Worker 内部的临时 rebind 被 restore 后，真正跨轮状态必须由返回值再次提交。

因此 non-overlap Scheduler 在 isolation 退出后明确执行：

batch.spec_info = batch_result.next_draft_input
batch.seq_lens  = batch_result.new_seq_lens
batch.input_ids = None

这不是重复工作，而是一次“选择性 commit”：保留下一轮需要的 bonus/new length，丢弃本轮只为 Draft/Target Verify 临时构造的 ScheduleBatch 字段绑定。

12.3.3 ScheduleBatch.input_ids=None 为什么仍有 Draft 输入

这里必须区分三个对象，不能只看同名的 input_ids：

对象/字段 第 N 轮结束后的值 作用
ScheduleBatch.input_ids None Scheduler 通用入口字段；清空以免复用本轮临时 Tensor

沿用 B=2、gamma=4 的具体数据，第 N 轮 Worker 返回：

Draft ForwardBatch.input_ids = flatten([
    [Z,M,M,M],
    [Q,M,M,M],
])

重建入口见 python/sglang/srt/speculative/dspark_components/dspark_worker_v2.py:482-488 和 python/sglang/srt/speculative/dspark_components/dspark_draft.py:361-415。完整 carrier 链是：

→ make_next_draft_input()
→ GenerationBatchResult.next_draft_input

所以：

≠ Draft model 没有 input_ids

12.4 overlap 的 FutureMap relay 边界

两种模式最终都要让 bonus 成为下一轮 anchor，但 transport owner 不同：

模式 下一轮 dSpark 状态的 carrier Scheduler 侧交接
non-overlap GenerationBatchResult.next_draft_input 同步返回后直接写 batch.spec_info；无需 future_indices
overlap FutureMap relay + next_draft_input.future_indices on_publish 提前发布，Scheduler 收到结果后再附加 indices，下一轮 resolver 解析

overlap 中 new_seq_lens 通过 on_publish/FutureMap 提前发布。Worker 构造的 next_draft_input 起初只有 bonus/new length 等状态；Scheduler 收到结果后才把 future_indices 附加到 batch.spec_info，下一轮再 resolve。不要用 non-overlap 的同步赋值时序 解释 overlap 的设备 Stream 完成时刻；也不要反向说“non-overlap 没有 FutureMap 对象”——对象 仍存在，当前 pure decode 只是没有通过它 relay dSpark extras。

13. 两轮连续时间线：rolling anchor 如何滚动

单轮快照不足以证明 bonus 如何成为下一轮输入。下面连续走两轮。

13.1 第 N 轮

轮前有效 KV： positions 0..21
prefix_lens： 22
anchor：      Y @ 22
drafts：      [a,b,c,d]
Target 输入： [Y,a,b,c,d]
接受：        [a]
bonus：       Z

用户输出：    [a,Z]
Draft KV 提交：[Y@22,a@23]
new_seq_len： 24
下一 anchor： Z@24

13.2 第 N+1 轮

假设 Draft 再提出 [e,f,g,h]，Target 接受 e,f，产生 bonus Q：

轮前有效 KV： positions 0..23
prefix_lens： 24
anchor：      Z @ 24
drafts：      [e,f,g,h]
Target 输入： [Z,e,f,g,h]
correct_len： 2
commit_lens： 3

用户输出：    [e,f,Q]
Draft KV 提交：[Z@24,e@25,f@26]
new_seq_len： 27
下一 anchor： Q@27

两轮连起来：

第 N 轮输出尾部 Z
        │
        ▼
第 N+1 轮 Target/Draft 输入头部 Z
        │
        ▼
第 N+1 轮提交 Z 的 hidden/KV

所以 bonus 的生命周期是：

本轮被预测并输出
→ 跨轮保存在 next_draft_input
→ 下一轮成为 anchor/input
→ 下一轮才产生并提交自己的 hidden/KV

14. 模式与高级边界

14.1 folded proposal 不等于 folded accept

proposal.folded=True 只表示 Draft CUDA Graph 已经包含 LM Head + Markov greedy sampler 等 tail；并不表示 Target accept 或 KV commit 也已折叠。

Worker 在 worker_v2.py:581-640 还要求：

verify epilogue 存在
+ proposal.folded
+ Target logits 调整为 no-op
+ 未启用模拟接受长度
+ 无 grammar
+ COMPACT
+ 本轮 Target 成功走 CUDA Graph

才令 folded_accept=True。此时 graph epilogue 已完成 greedy accept/finalize/build-output，Python 侧 accept_and_finalize() 只读取缓冲。

folded_accept 仍不必然等于 folded_commit。只有 epilogue/pool 支持融合 KV 写入时才跳过 commit_hidden()；普通 dense 路径仍需注入 Target hidden。

14.2 COMPACT 与 CUDA Graph 也是两个维度

COMPACT：决定是否在 Target 前裁掉未选 candidates，并选择 graph_num_tokens 容量
CUDA Graph：决定这组 shape/key 是否可 replay

COMPACT 可以走 eager；CUDA Graph 下还可能包含 tier padding；layout fallback 时也会回到 full-width non-compact。有 CUDA Graph 不自动意味着 accept/commit 都 folded。

14.3 DeepSeek-V4

本文的 [B,G,H_d] 是 dense 主线教学形状。DeepSeek-V4 draft hidden 带 hc_mult 维度，需要 collapse 后再进共享 LM Head，并使用专用 attention backend；MLA pool 还可能支持 folded commit。不要把 dense hidden shape 和 KV 注入路径硬套到 V4。

14.4 硬件与并行限制

当前 dSpark 参数处理要求 CUDA 设备字符串并限制 PP=1；DP Attention 还有 LM Head、MoE、 CP 等额外准入条件。本文没有把 generic CUDA/ROCm worker 外层能力错误外推为 dSpark 的 ROCm 支持。相关入口见 python/sglang/srt/arg_groups/speculative_hook.py:278-308。

仍使用：

  2. 此时用户有效输出、Draft KV 新提交、下一轮 anchor 分别是什么？
  3. 若四个 draft 全部接受，最大有效输出长度是多少，最后一个 bonus 来自哪一行 Target logits？
  4. 为什么本轮不能直接把 Q 写入 Draft KV？
  5. 若 CAP_ACCEPT 给出 verify_len=2，它最多允许接受几个 draft？Target 是否只 forward 两行？
  6. ordinary non-overlap dSpark pure decode 会不会调用 resolve_forward_inputs()？为什么通常没有状态变化？
  7. Scheduler 把 batch.input_ids 清成 None 后，下一轮 Draft ForwardBatch.input_ids 从哪里来？
  8. 一个 token 的多个 Target layer feature，怎样变成多个 Draft layer 的 K/V？这些 K/V 是否相同？
参考答案
  1. commit_lens=3，new_seq_lens=25。
  2. 输出 [a,b,Q]；Draft KV 新提交 [Y@22,a@23,b@24]；下一轮 anchor 是 Q@25。
  3. 最大长度 gamma+1=5，输出 [a,b,c,d,bonus]；bonus 来自输入 d 那一行的 Target next-token 分布。
  4. Q 只是由输入 b 的 logits 得到的输出，本轮没有作为 Transformer 输入，尚无自己的 hidden/KV。
  5. 最多接受 verify_len-1=1 个 draft；CAP_ACCEPT 仍 forward 完整五行。COMPACT 的逻辑有效 candidates 才是 [Y,a]，物理 forward 长度仍是 graph_num_tokens，可能带 tier padding。
  6. 会真实调用；只是 prefill staging、ordinary non-spec gather、overlap spec-extras 三条修改路径的 guard 在该状态下都不满足，所以是 guard-only no-op。Prefill/Mixed 边界不能套用此结论。
  7. GenerationBatchResult.next_draft_input 被同步写入 batch.spec_info；下一轮 proposer 取出 bonus_tokens，写入 draft_block_ids[:,0]，再 flatten 成 Draft ForwardBatch.input_ids。
  8. 多个 Target feature 先拼接并经 project_target_hidden() 融合成一个 ctx_hidden_t；同一个 ctx_hidden_t 再进入各 Draft layer 不同的 KV projection，得到每层不同的 K/V。只有 commit_lens 覆盖的 token/位置会写入 Draft KV。
