03 · Draft 提案

Transformer 一次并行得到四个槽位；Markov 小头再串行生成 a→b→c→d

Draft 模型真正 forward 的输入是 [X,MASK,MASK,MASK]，不是最终候选 [X,a,b,c,d]。后者直到 DraftProposal 返回、Target 候选矩阵装配时才出现。

关键不变量 · W=G+1=5，Draft Transformer 只运行 G=4 行对象边界 · MASK 形状与真实 draft tokens 分开保存证据范围 · 当前源码 f01a0c7f97ec · 静态核验
输入 · 跨轮状态draft_input : DFlashDraftInputV2 提供 anchor X；batch : ScheduleBatch 提供 prefix 与请求索引。
输入 · 本轮预留verify_window : VerifyWindow 已为每请求预留 W=5 个 Target verify 位置。
输出 · 提案对象proposal : DraftProposal 携带真实 token、hidden、采样分布材料与可选 confidence。
下一消费者self : DSparkWorkerV2 取 token；04 的 self._verify_planner 计算 budget/layout。

STATIC · 贪心

每个 step 使用 argmax(step_logits)。proposal 可折叠并不保证后续 accept 折叠；04 的 STATIC 仍得到 layout=None。

COMPACT · 随机采样

按每请求 temperature 与 greedy mask 采样，并保留 corrected_logits + temperatures；06 用它们重建实际 P_D。

FOLDED · 贪心

仅当 draft sampler 存在、Draft CUDA 图命中且全贪心，token 才直接读 graph buffer；此时 corrected_logits=None。

辅助视图 · 两种长度语义

seq_lens=[20] 与 seq_lens_cpu=[24] 同时成立，但不是同一个概念

前者保留请求进入 verify window 前的设备侧 prefix 边界；后者把本次 Draft 的四个 token 行计入 CPU 侧总 token 计数。它们都不表示“a,b,c,d 已被 Target 接受”。

03A · 进入 Markov Head 内部机制 →逐步观察四个 hidden 同时完成后，为什么 logits 修正与采样仍必须按 X→a→b→c→d 串行。
为什么、如果省略、易错边界与源码锚点
为什么 · W 比 G 多 1

Target 验证还需要 anchor 所在行预测第一个 draft token，因此窗口是 anchor + G drafts。

易错 · TARGET_VERIFY 的接收者

模式用于复用 block-shaped runner/attention 分派；实际接收者仍是 Draft ModelRunner，不是 Target worker。

如果省略 Markov

直接独立采四个 base logits，会让 b/c/d 看不到 a/b/c；proposal 与实际 P_D 都改变。

如果丢失 corrected logits

sampling 路径无法重建 Markov 修正与 temperature 后的 proposal 概率；06 不能正确做拒绝采样修正。
