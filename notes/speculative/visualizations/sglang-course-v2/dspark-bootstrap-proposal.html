01直接结论

DSpark 的第一轮不是凭空得到 gamma 个draft token。target prefill先生成一个next token，这个token成为rolling anchor；同时target auxiliary hidden经过 TargetHiddenKvInjector写成draft模型可读的KV。decode时 DraftBlockProposer构造长度为 gamma 的draft输入 [anchor, MASK, ..., MASK]，draft forward为这gamma行产生hidden；随后base logits与Markov head以“前一个真实/已采样token”为条件，顺序采出 d1…d_gamma。target最终验证的却是宽度 gamma+1 的 [anchor,d1,…,d_gamma]。

rolling anchor解决了自回归边界的一个偏移：本轮用户输出是若干accepted draft加新bonus，但target KV实际提交的输入链是旧anchor加accepted drafts；新bonus尚未作为input经过target，留给下一轮做anchor。于是“输出长度”和“提交KV长度”相同，内容却错开一位。new_seq_lens=prefix_lens+commit_lens只表示前沿位置推进，绝不能解释成新bonus已经拥有target KV。本页先建立这个proposal坐标，confidence和ragged layout留到下一页，accept/KV回收留到再下一页。

02当前路径假设

主线是CUDA、DSPARK、pp_size=1、gamma=4、verify width=5、普通文本R0、greedy、无grammar、无logit adjustment、static或尚未改变proposal的ragged配置。target与dense draft模型在同一worker进程，draft checkpoint提供合法 mask_token_id 与Markov head；target暴露lm head，worker把target embedding/lm head附给draft所需模块。是否走draft CUDA Graph不改变proposal对象，只会决定greedy sampler/head/confidence是否折叠到graph尾部。

DSpark允许一组受限DP attention组合：dense draft可切换draft TP context；DeepSeek-V4 MoE draft有额外attn_tp和collective守卫、idle rank参与逻辑。CP在DP模式被启动校验拒绝，PP不支持，mixed chunked prefill关闭。这里使用单rank示例，不把single-rank的调用完成视为多rank collective/device completion证据。当前worker也直接拒绝 return_logprob。

03输入、本页职责与输出

prefill输入是target生成结果、FULL auxiliary hidden、extend/prefix lengths和out-cache locations；输出是已写好的draft KV以及 DFlashDraftInputV2(bonus_tokens,new_seq_lens)，DSpark复用该跨轮容器但不复用DFlash block算法。decode proposal输入是anchor、prefix lengths、为宽度5预先准备的verify slots、sampling info、target embedding以及draft模型。输出 DraftProposal 包含输入block ids、真正draft tokens、draft hidden、可选confidence/tap和 folded标记。

04为什么存在

mask block让draft模型一次计算多个位置hidden，而Markov head在其上补回token间依赖。若直接对每个位置base logits独立argmax，d2不知道已经选了d1，proposal不再对应一条条件链；markov_head.sample_block()接收anchor、draft hidden和step sampler，逐步以先前token embedding修正logits。对non-greedy请求，step sampler还按每请求temperature与greedy mask选择multinomial或argmax；因此proposal对象保留corrected logits，供后续rejection sampling使用。

target embedding/lm head共享是当前模型接口的一部分，不表示draft和target整模共享权重。worker显式找到target lm_head.weight并调用draft attach_shared_modules()；draft transformer/Markov/confidence头仍来自draft checkpoint。缺少lm head、Markov head或mask token会在初始化/运行时报错，而不是自动退化成普通decode。

prefill hidden注入必须先于第一轮proposal。anchor只告诉draft“最后一个token是什么”，不足以重建长prompt的attention上下文；TargetHiddenKvInjector把target隐藏表示通过draft模型的写入接口变成draft KV。反过来，仅有KV没有anchor也不够，因为 [A,M,M,M] 的第一行必须用上一轮target预测token启动滚动链。

05对象与状态

DSparkWorkerV2是组合根：_target_worker负责真实target；_draft_worker/draft_model_runner/draft_model负责mask-block forward；_kv_injector维护draft KV；_proposer生成候选；_verify_planner决定预算/布局；_verify_executor做target和accept；observer只记录，不控制写入。初始化还把 gamma 与 verify_num_draft_tokens=gamma+1分开保存，这比沿用一个模糊的 num_draft_tokens更能防止off-by-one。

DraftForwardResult保存draft_block_ids、raw hidden、三维hidden与graph命中；DraftBlockResult保存真正的draft tokens、sampling所需corrected logits、greedy mask和temperatures；DraftProposal把两者合并，并附带confidence或confidence tap及folded。folded=True只说明draft greedy proposal来自CUDA Graph尾部buffer，不说明target accept或KV commit也折叠，后者有独立守卫。

verify slots在proposal前由alloc_verify_window()从target req_to_token映射得到，包含position与 [B,gamma+1] cache loc。draft forward只使用前gamma列写自己的block状态；target verify使用完整gamma+1列。预留地址可先存在，但R0的Req.kv_committed_len仍由稍后的result processor推进。

组件图显示了 DSparkWorkerV2 为什么是“编排者”而不是又一个模型。proposal、confidence/layout、target verify/accept、hidden-to-draft-KV 分别有独立 receiver；observer 只旁路观测，不参与 token 或 KV 的正确性裁决。

06当前源码调用链

_forward_prefill()调用target并要求FULL hidden，把batch_output.new_seq_lens设为当前seq lens并publish；随后验证hidden、extend/prefix/out loc存在，计算positions，调用injector写draft KV，清掉公开结果中的hidden，再以target next_token_ids构造首个anchor状态。

_forward_decode()确保batch.spec_info是 DFlashDraftInputV2，为R0分配verify window，然后进入draft context调用DraftBlockProposer.propose()。proposer的_run_forward()建立 [A,M,M,M]，positions与cache loc取verify window前gamma列，构造 ForwardBatch(ForwardMode.TARGET_VERIFY,spec_algorithm=DSPARK)并运行draft runner。得到hidden后，如果draft graph sampler可用、graph命中且全greedy，就直接读取其tail buffer；否则调用compute_base_logits()并以sample_draft_block()逐步采样。worker随后取得proposal，才进入confidence、budget、layout和target verify阶段。

下图只跟踪形状与 rolling anchor，不画 confidence 与 accept 细节。gamma=4 时 draft runner 输入是4行 mask block，Markov head 产生4个真实 draft token，target verify 则需要 gamma+1=5 行；这是两种宽度合同，不是某一处 off-by-one。

07连续例子

沿固定样例逐步运行切换步骤时同时观察对象、状态与下一消费者

t0，R0 prompt长度100。target prefill输入最后一个prompt token，在位置0～99写target KV，输出next token A和每个extend row的aux hidden。injector将这些hidden写成draft KV；此时用户还未收到后续block，但A作为prefill结果会进入普通结果流程并成为下一decode轮的anchor状态。

t1，decode前缀frontier记为100，anchor A代表将被放在位置100作为target输入。alloc_verify_window()准备positions [100,101,102,103,104]及对应5个slot。proposer只取前4个slot，构造 [A,M,M,M]并运行draft；得到hidden [h0,h1,h2,h3]。base head产生每位置初始logits，Markov head以A为第一个prev token采出d1，再以d1影响d2，依次得到[d1,d2,d3,d4]。

t2，worker构建target输入 [A,d1,d2,d3,d4]。假设target只认可d1,d2并产生新bonus B，则本轮输出 [d1,d2,B]，commit_lens=3，KV逻辑输入链是 [A,d1,d2]，new seq lens=103。位置103的B还没有作为target input写KV；它被放入下一轮 next_draft_input.bonus_tokens。

t3，第二轮的prefix=103、anchor=B。新的verify input从 [B,e1,e2,e3,e4]开始；如果错误地认为B在上轮已经有KV并从位置104开始，positions会整体错一位。连续两轮的rolling例子说明同一个commit_lens同时描述输出数和target输入KV数，但两组token内容是“右移一位”的关系。

08为什么必须在这里

injector必须在prefill结束且target hidden可得时执行，因为更早没有target语义特征，更晚第一轮draft已经需要prompt上下文。draft_block_ids[:,0]必须在proposer内从最新 bonus_tokens拷入，不能仅使用Req.output_ids[-1]：overlap下上一轮结果可能尚未被CPU result processor写入Req，而FutureMap已经发布了device上的真实anchor。

Markov采样必须在draft hidden出来后，因为base logits/confidence tap依赖这些hidden；又必须在target verify之前，因为verify需要真实候选而不是MASK。confidence/layout必须放在proposal之后，是因为它们评估的是当前draft位置；但budget在overlap下可能来自历史relay，这一“历史决定多少、当前confidence决定给谁”的分工将在下一页展开。
