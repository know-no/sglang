01直接结论

DSpark verify的一次target forward会在候选窗口的slot中写target KV并返回每行logits/aux hidden，但“写过”不等于“提交”。accept只允许从anchor后的draft链连续向前：correct_len=k表示前k个draft被target接受；target在下一位置产生bonus；commit_lens=k+1同时是本轮输出数与KV逻辑推进数。用户输出是 [d1…dk, bonus]，target KV应保留的输入链是 [old_anchor,d1…dk]，两者长度相同、内容右移一位。

compact只计算每请求 verify_lens 指定的真实rows，随后把logits、hidden和候选散回固定 [B,verify_width] stride；缺失列明确填0，再由cutoff阻止这些padding进入提交。full-forward cap-accept则仍计算完整width，只在accept阶段把可提交深度截到 verify_lens-1。因此只有full-forward的trim可以表达“target确实算过、但因cap没有提交”的正确draft数；compact的0填充不能提供未计算列的反事实正确性。接受后commit_hidden()仅把accepted prefix的target hidden物化到draft KV。Scheduler稍后根据accept_lens、grammar、retract/finish状态推进 Req.kv_committed_len 和 output_ids；未提交候选slot可以被后续轮次覆盖，最终finish/retract由release_kv_cache()回收allocated尾部。

02当前路径假设

主线为CUDA dense DSpark、R0/R1普通decode、gamma=4、verify width=5、greedy、无grammar、无simulate accept、非folded eager accept；先给compact verify_lens=[4,2]示例，再指出non-compact差异。target attention backend支持对应ragged metadata，worker已通过PP/DP/CP启动守卫。public return_logprob仍被拒绝，aux hidden只作内部KV注入。

sampling请求会构造draft probs并走AcceptSampling，混合batch按greedy mask选择两组结果；grammar会先对所有strided target logits应用mask且禁用folded accept。Mamba/ReplaySSM有额外state commit helper，DP idle rank有dummy target-verify参与。本页说明分支边界但不宣称这些后端在当前环境已运行，也不把Python kernel调用当设备同步完成。

03输入、本页职责与输出

输入是proposal [old_anchor,d1…d4]、完整verify window、可选ragged layout、sampling info和prefix lengths。DSparkWorkerV2._forward_decode()是编排receiver；TargetVerifyExecutor不是一次完成全部工作的黑盒，而是由worker分三次调用：先 run_compact()/run_non_compact()，再 accept_and_finalize()，最后在未folded时 commit_hidden()。grammar mask和FutureMap发布都发生在这些调用之间。输出AcceptOuts包含correct drafts、bonus、cap trim、commit lengths、新序列长度与固定stride padded tokens；外层再打包为GenerationBatchResult。

字段 R0 示例 是否控制写入 语义
verify_lens 4 控制target物理/accept可见窗口 anchor + 最多3个draft位置
correct_len 2 是，决定accepted drafts target连续认可d1,d2

04为什么存在

target必须并行计算候选后才能知道连续正确长度，因此verify slots要先分配，KV写入也会覆盖所有实际forward rows。若accept kernel直接删除rejected KV或修改allocator，它会与graph/eager、DP padding、overlap result延迟纠缠，并让下一轮地址不稳定。当前设计让地址和内容可超前写，逻辑提交由commit_lens及Req frontier限定；拒绝尾部不是可见prefix，之后相同逻辑位置可以被新proposal覆盖。

固定stride输出让Scheduler无需理解每请求ragged长度。next_token_ids仍按verify_num_draft_tokens分块，accept_lens告诉CPU每块取多少；如果用ragged总数作为stride，第二个请求的起点会随第一个请求accept数变化，overlap buffer与graph static storage都难以复用。padding 0不进入Req，因为processor只切有效前缀。

draft KV commit必须读取target hidden而非draft hidden。draft hidden描述proposal模型对mask block的表征，不能证明target接受后的上下文；target verify hidden对应target已计算的真实输入行，再经draft模型投影写入draft KV。只写commit_lens前缀保证下轮draft不会关注已拒绝的d_(k+1)。

05对象与状态

VerifyWindow先为每请求建立positions_2d=prefix+offsets与完整 [B,width] target cache loc。compact时 BuildRaggedVerifyWindow按verify_lens压紧token、position、cache loc到graph_num_tokens；target结果仍是compact rows。executor随后通过ScatterCompactToStrided恢复 [B*width,*]，logits与hidden未验证列用 0.0 填充，graph epilogue也把候选缺列填0，使logit adjustment与accept共享一个逻辑几何。这里的0只是静态布局占位符：cutoff保证它不能增加commit，但若某个metric读取padding产生的cap_trim_lens，也不能把它解释为target在这些位置“本来会预测正确”。当前 maybe_observe()在compact模式直接warning并跳过debug confidence metrics，正是因为padding会污染per-position prefix label。

accept_draft_tokens()从DraftBlockResult.greedy_mask分派。全greedy直接调用AcceptGreedy；全sampling由corrected logits/temperature生成draft probs并调用AcceptSampling；混合batch两边都算后用SelectMixedAccept逐请求选。FinalizeAcceptLens计算commit_lens=correct_len+1与new_seq_lens=prefix+commit，BuildOutTokens把accepted drafts与bonus放在前部。

KV要区分target与draft。target verify按batch.out_cache_loc写target pool；非compact commit_hidden()从logits_output.hidden_states.view(B,width,H)取全部物理行，却把cache_loc_2d和commit_lens交给prefix-valid injector。compact先将hidden散回strided，再由inject_ragged()构造commit布局。这里完成draft KV内容对齐，但并不在CPU Req上推进committed字段。

等待D2H不是 _resolve_spec_v2_tokens() 的内部职责。真正receiver是外层 BatchResultProcessor.process_batch_result_decode()：它先对 result.copy_done.synchronize()，然后才进入spec-v2解析；此时 _resolve_spec_v2_tokens()只断言CPU tensor、读取accept lens、处理grammar retained prefix，并对仍有效R0增加实际保留token数。随后decode loop追加output并更新finish；finish时release_kv_cache()让prefix cache只处理effective_kv_committed_len，再释放到kv_allocated_len的尾段。这才是allocator意义的reclaim，不应在accept kernel旁虚构“立即free每个reject slot”。

先看组件所有权：target executor 同时调用 target model、accept kernels 与 hidden injector，但它不持久更新 Req；FutureMap 只保存下轮调度需要的 device frontier；唯一会将最终 retained tokens 写入 Req.output_ids/kv_committed_len 的是 CPU result processor。

06当前源码调用链

worker先根据mode第一次调用executor的run_compact()或run_non_compact()。non-compact构造完整DFlashVerifyInput，调整host seq lens上界后调用target forward_batch_generation(is_verify=True)；compact先build ragged window、设置epilogue buffers，再执行ragged target，最后scatter回strided并应用logit adjustments。第一次调用返回后，若有grammar，worker在第二次executor调用之前构造linear tree mask并作用于每行logits。

worker第二次调用accept_and_finalize()；folded fast path只读取graph epilogue buffers，本页eager主线则调用accept_draft_tokens()、可选simulate override、finalize和out-token builder。worker随后调用 on_publish，其具体receiver是overlap Scheduler绑定的 FutureMap.publish(future_indices, ...)。只有当target graph epilogue已经融合commit时才跳过第三次调用；否则worker第三次调用commit_hidden()。返回结果时accept_lens=commit_lens，block_accept_lens=commit_lens+cap_trim_lens只供metrics，cap_lens=verify_lens记录窗口。CPU result processor以固定width stride切片，才持久提交；其中 copy_done.synchronize()在process_batch_result_decode()外层，不在_resolve_spec_v2_tokens()内。

下图用 R0/R1, width=5, verify_lens=[4,2] 把一个 compact batch 拆成六类结果。特别注意：raw acceptance 是 device kernel 输出，padded result 是跨 device/CPU 的固定 stride 合同，user-visible output 还要经过 grammar/finish/retract；三者不能用一个“accepted tokens”箱子取代。

07连续例子

t0，R0 prefix=100，R1 prefix=50，width=5；完整地址窗口已映射。layout给verify_lens=[4,2]：R0 target真实输入 [A0,a,b,c]，R1 [A1,x]，compact总有效6行，graph bucket可能8。R0的d和R1的y,z,w本轮不进入target真实verify；bucket多出的2行只是padding。

t1，compact target对R0确认a,b，下一预测B0，所以correct_len=2、commit=3、输出[a,b,B0]、cap_trim=0。对R1仅真实计算 [A1,x] 两行，确认x后由已计算的第二行logit产生B1，所以correct_len=1、commit=2、输出[x,B1]、本例cap_trim=0。R1的y,z,w对应候选、logits和hidden列都只是0 padding；源码无法据此回答“若继续全宽，y是否正确”，因此课程也不做这种反事实推断。

t1b，另取full-forward cap-accept请求R2：width=5全部真实计算，verify_lens=3只允许anchor后最多2个draft。若target在完整结果上连续确认u,v,w，accept先得到raw correct=3，再由 capped=min(3,3-1)=2 得到correct_len=2、cap_trim=1、commit=3。这里trim有意义，因为w所在行确实由target计算过；这与compact缺失行填0是两种不同证据。

t2，target KV逻辑保留R0 [A0,a,b]三行、R1 [A1,x]两行；draft hidden injector也只写这些prefix。输出却分别以B0/B1结尾，它们进入下一轮anchor。结果buffer按width=5放 R0:[a,b,B0,0,0]、R1:[x,B1,0,0,0]；R1切片起点仍是5，不是R0 commit数3。

t3，CPU processor若无grammar/retract，将R0 committed 100→103、R1 50→52，再扩output。若R1在延迟结果处理前已retract，则不推进其Req；其allocated尾部由retract/release路径回收。t4，下一轮R0以prefix103、anchorB0覆盖位置103之后的新verify窗口；旧rejected rows不是可访问committed prefix。

08为什么必须在这里

ragged pack必须在target forward前，scatter必须在统一accept前。若直接在compact buffer上用固定stride accept，R1行起点会按R0 lens变化；若不scatter又复用现有sampling/logit adjustment kernel，索引会错误。accept必须在grammar/logit adjustment之后，否则target裁决的分布与API约束不一致。

hidden commit必须在accept之后才能得到commit_lens，但要在下一轮draft读取这些slot之前完成。Req committed推进更晚，在CPU result processor，因为只有它能处理grammar retained run、finish与retract。finish释放又必须使用committed frontier，而不是本轮verify width，才能既保留可缓存prefix又释放over-allocation。

11自测

  1. correct_len=2时commit_lens为何是3？输出token与target KV输入token分别是哪三项？
