three acceptance paths

greedy、sampling、mixed：相同输出合同，不同验收语义

MAIN · GREEDY

逐位置 equality

target_predict = argmax(target_logits) correct_len = first mismatch index bonus = target_predict[correct_len]
  • AcceptGreedy.execute()。
  • 没有拒绝采样概率修正。
  • 若 layout 截断，则 CapCorrectLen 重新截断并在新位置取 bonus。
DATA · SAMPLING

使用真实 q 做拒绝采样

q = softmax(corrected_logits / temperature) p = target distribution after temperature/top-k/top-p accept draft x with min(1, p(x)/q(x)) reject → sample from normalized [p-q]₊
  • SoftmaxTemp.execute() 重建 proposal q。
  • Target p 由 SoftmaxTemp 或 top-k/top-p helper 构造。
  • 最终 bonus 由随机数与修正分布决定，可能不是 argmax。
GUARD · MIXED

同一 batch 逐请求选择

greedy_out = AcceptGreedy.execute(...) sampling_out = AcceptSampling.execute(...) out = SelectMixedAccept.execute(greedy_mask, ...)
  • 不是整批强制一个算法。
  • draft_block.greedy_mask[req] 决定每个请求选哪组结果。
  • 最终仍收敛到同一个 AcceptOuts 数据结构。
关键纪律： sampling verify 使用的是 Draft 当时真正用来 proposal 的分布 q。如果只保留 token 而丢掉 corrected logits/temperature，就无法保持 Target 原始输出分布。

before → writes → after

具体 token 账本：[X,a,b,c,d] 如何得到 [a,Y]

设 prefix_lens=[20]、gamma=4、W=5。Target 在 X 后预测 a，在 a 后预测 Y；因此只接受一个 Draft token。

BEFORE

verify_ids_2d / Target predict

candidates 包含 anchor 与四个 drafts。Target 的每一行预测下一 token。

Xabcd
aY………
WRITES

accept + finalize

a 匹配，b 与 Y 不匹配；在 sampling 路线，Y 仅代表本例采样结果。

a ✓b ✕cd
correct_len = [1] bonus = [Y] cap_trim_lens = [0] commit_lens = correct_len + 1 = [2] new_seq_lens = prefix_lens + commit_lens = [22]
AFTER

BuildOutTokens backing

先复制 drafts，再把 index=correct_len 改写为 bonus。有效输出只看前 commit_lens 项。

aYcd0
physical backing = [a, Y, c, d, 0] semantic output = backing[:commit_lens] = [a, Y] c / d / 0 are OFF: not committed
容易误读的实现细节：BuildOutTokens 并不把 bonus 之后的所有槽都清零。源码先复制 [a,b,c,d]，再 scatter Y 到 index 1，所以 backing 是 [a,Y,c,d,0]；commit_lens=[2] 才是有效边界。

AcceptOuts fields

六个字段各自控制什么

correct_len[1] · route-dependent dtype接受的 Draft token 数，不包含 bonus。sampling/mixed 路径为 int32；普通 greedy 的 Torch reduction 与 folded buffer 为 int64，不能假设全路径统一 int32。
bonus[Y] · int64拒绝位置/链尾的 Target 修正采样 token；下一轮 anchor。
cap_trim_lens[0] · int32因 verify_lens 截断而未计入 commit 的潜在正确 drafts；主要进入 metrics。
commit_lens[2] · int32correct_len + 1，唯一的 out_tokens 有效前缀长度。
new_seq_lens[22] · prefix dtypeprefix_lens + commit_lens，传给发布与下一轮状态。
out_tokens[[a,Y,c,d,0]] · int64固定 stride backing；消费者必须结合 commit_lens 解释。

why / omitted / source / evidence

为什么必须在这里 finalize

MAIN

WHY HERE

只有验收结束后，系统才同时知道“接受了几个 Draft”与“必须额外提交的 bonus”。因此 commit_lens=correct_len+1 不能在 proposal 或 Target forward 前提前决定。

FAIL

IF OMITTED

若把 correct_len 当提交长度，会漏掉 bonus；若把整个 backing 当有效输出，则会把已拒绝的 c/d 泄漏给用户并推进错误的序列长度。

GUARD

BOUNDARY

cutoff_layout.verify_lens 可限制 correct_len 并重取 bonus；SGLANG_SIMULATE_ACC_LEN 是测试/模拟覆盖。Folded 路线把相同输出合同放入 CUDA graph，见 08。
