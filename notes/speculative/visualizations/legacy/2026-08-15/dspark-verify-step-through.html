TWO PHYSICAL RAILS

同一候选语义，两种 Target 行布局

MAIN · run_non_compact()

  1. verify_ids_2d [B,W] 全部 flatten 为 [B×W]。
  2. DFlashVerifyInput(draft_token=..., positions=..., draft_token_num=W)。
  3. Target 对每个 request 的 W 行都 forward；无需 layout/scatter。
  4. 输出已经是固定 stride：[B×W,V] 与 [B×W,H_aux]。

CUDA · run_compact()

  1. BuildRaggedVerifyWindow.execute(...) 按 verify_lens 压紧有效行并 pad 到 graph tier。
  2. _run_ragged(batch, layout, ragged_window, sampling_info) 只让 Target forward graph-tier 行。
  3. graph epilogue 或 ScatterCompactToStrided.execute() 恢复 [B×W,*]。
  4. 无效列填 0，后继仍使用统一 stride contract。

WHY HERE · FAILURE MODES

为什么压紧后还要 scatter，为什么 metadata 必须预先准备

MAIN · WHY TARGET GETS ANCHOR + DRAFT

Target 必须看到每个候选位置的真实前缀，才能一次 forward 得到 row(X)→a、row(a)→Y 等下一 token 分布。

CUDA · WHY COMPACT

budget/layout 减少实际 Target 行；graph tier 只补必要 padding。scatter 让接受核与 hidden commit 继续使用固定 B×W 索引。

FAIL · OMIT ANCHOR / SHIFT

第一行没有 anchor，或 candidates 使用错误拼接顺序，全部 next-token logits 都错位；接受长度失真。

FAIL · OMIT SCATTER / METADATA

compact 行被误当 fixed stride，request 边界错；或 attention 看不到 prefix KV + verify window KV，Target 计算的上下文不完整。
