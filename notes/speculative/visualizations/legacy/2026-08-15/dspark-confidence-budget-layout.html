Planner 接收什么、改什么、返回什么

RECEIVES

proposal: DraftProposal、draft_input: DFlashDraftInputV2、当前 prefix_lens/req_pool_indices；proposal 可能已带 folded confidence。

MUTATES

RETURNS

NEXT CONSUMER

two-round history

启用 budget scheduling + 默认 lag=2：overlap 与 non-overlap 都让 budget 看两轮前

它们只是“延迟放在哪里”不同。当前 confidence 仍立即用于本轮 top-k 分配，所以同一轮同时存在历史轴与当前轴。

t−2 · confidence请求 R0/R1 的 confidence 产生，并携带 req generation。C[t−2]
OVERLAP RELAYConfidenceRelay 的 CUDA host ring 固定 lag=2；FutureMap 在 t 解析。relay_ring_lag = 2
NON-OVERLAP CARRY没有 FutureMap relay；Host planner 的本地 carry_steps=2 将当前输入移成历史。lag_steps=2 − relay_lag=0
t · BUDGET两条路径汇合为历史 survival，与 SPS cost 计算“总共多验证多少”。budget = argmax θ(k)
t · ASSIGN同一轮刚生成的 C[t] 做 cumprod/top-k，决定 extra token 分给哪个请求。verify_lens = 1 + selected_extra
GUARD · request identity：req_generation 必须与当前 pool slot generation 匹配；不匹配时 history survival 退回全 1，避免复用 req_pool slot 后把上一请求的 confidence 泄漏给新请求。
OFF · boundary：relay 尚未初始化/事件未 ready 时可能解析为 None，planner 会走无 budget 的退化路径；这不证明每个启动阶段都有可用的两轮历史。

budget=0 ≠ budget=None：0 是有效调度决策，top-k 不选 extra，每请求仍得到最小 verify_len=1；None 表示这轮没有 budget 控制信息，_schedule_verify_lens() 返回 None，随后由 mode 的 fallback 规则决定 layout。
为什么没有 profiled SPS 仍返回 uniform COMPACT layout：_is_verify_all 让 schedule_layout() 从 cache 返回固定 uniform layout，跳过每轮 schedule/host-device round-trip；它保留 COMPACT 的 graph/metadata 形态，但验证全部 token，所以没有调度收益。

why here / omitted failure

Planner 的正确性边界与性能边界

WHY HERE

DraftProposal 返回后才有本轮真实 token 与 hidden/confidence；在 Target launch 前算 layout，才能让 05 选择物理 rows。更早没有当前 proposal，更晚已经无法减少 Target 计算。

FAIL · STALE IDENTITY

若历史 confidence 不校验 req_generation，pool slot 被新请求复用后会继承旧请求 survival，budget 发生跨请求污染；这是调度状态正确性问题。

PERF · NO SCHEDULE

缺 budget/confidence 时主要退化为 full/uniform verify，Target 分布仍由 06 的 acceptance 保证；损失通常是验证成本/吞吐收益，不等同于跳过 Target 或直接产生错误 token。
